# 视频超清增强方案审核与补强方案

> 审核对象：`docs/视频超清增强实战修正架构(补充) (2).txt`
> 审核日期：2026-08-06

## 一、结论

DeepSeek 这个方案的方向是对的，但“9 类 850 段可证明覆盖所有真实视频”的说法被高估了。

方向正确的部分：

- 用 RRDBNet 做离线超分，而不是轻量实时模型；
- 3 帧输入、9 通道时序融合，而不是逐帧独立超分后再补光流；
- 二阶随机退化工厂，而不是固定退化流程；
- 按场景补数据，尤其是人物、文字/UI、低光、高速运动；
- 训练阶段加入 GAN 预热、R1、梯度裁剪，与项目已落地的 `python/sr/train.py` 一致。

需要修正的部分：

- “9 类是 3 个维度的笛卡尔积最小覆盖集”不是数学证明。纹理、光照、动态并不互相独立，人物/风景/食物/动物/艺术更多是内容类别，不是三个正交因子。9 类只能算工程上的常用覆盖策略，不能保证 90% 场景不翻车。
- “PSNR 28.5~29.5、LPIPS 0.18~0.22、接近 Topaz Video AI 中等预设”属于未实测的推测，不能作为交付承诺。
- “1080p→4K 约 8fps”需要按实际模型、tile、ONNX Runtime 和 GPU 实测。当前推理默认是 `tile_size=256 / tile_overlap=32`，不是方案里的 `320/32`。
- 当前项目 v1 训练目标是 `scale=2`。UI 虽然有 3×/4× 选项，但必须分别训练并导出对应 scale 的模型，或做级联，不能默认 3×/4× 已可用。

### 滚动弹幕和屏幕录制是否已有

数据层面：

- 全库检索未发现 `danmaku`/`弹幕` 素材，只有 `scrolling codes`、`scrolling social media` 等近似内容。

### 食物/动物/艺术是否已有

没有。`python/sr/dataset.py` 的 `SCENE_CATEGORIES` 是 6 类，`scripts/fetch_public_sr_data.py` 和 `MANIFEST.json` 也没有这三类。

## 三、缺口判断

### 1. 食物/动物/艺术：建议补，但不阻塞 v1 首训

这三类在短视频场景里很常见，纹理特征也明显不同：

- 食物：高饱和、多汁高光、热气和微距纹理；
- 动物：毛发、羽毛、鳞片等随机重复纹理，且常伴随运动；
- 艺术：插画、动画、油画、像素艺术等非照片纹理，硬边和色块规律不同于实拍。

它们不是当前训练能否启动的前提，但会影响通用泛化。建议在完成现有 6 类真实权重训练后，作为 P1 扩展采集。

### 2. 滚动弹幕和屏幕录制：有必要，但作为 `text_ui` 子类

结论：有必要，不是为了做软件功能，而是因为它们是超分模型会真实遇到的输入类型。现有 `text_ui` 只能覆盖“像屏幕”，不能覆盖“真正是屏幕录制/弹幕”的退化表现。

| 素材 | 必要性 | 建议量 |
|---|---:|---:|
| 屏幕录制 | 有必要。真实用户会导入 IDE、浏览器、办公软件、录屏教程；这类内容文字多、UI 边线锐利、滚动和静态区域共存，模型不见过就容易把字抹糊 | 30~50 段 |
| 滚动弹幕 | 有必要，但优先级低于屏幕录制。弹幕是移动小字，属于文字/UI 的一个特殊时序形态；若产品面向弹幕、直播回放、二次元内容，必须补，否则横向滚动小字容易粘连和闪烁 | 20~40 段 |

理由：

- 弹幕和录屏都依赖文字/UI 的精确硬边先验，和普通 UI 共用同一类学习目标；
- 弹幕额外包含滚动位移，录屏额外包含连续 UI 变化和静态区域；
- 不需要把它们拆成两个独立大类，否则数据量和训练复杂度会无谓增加。

建议在 `text_ui` 下按子目录组织：

```text
data/sr_train/text_ui/
├── static/            # 静态文字、字幕、界面
├── danmaku/           # 滚动弹幕
└── screen_recording/  # 屏幕录制
```

采集量建议：

- 滚动弹幕：30~50 段；
- 屏幕录制：30~50 段；
- 弹幕最好用自己生成或自己录制的 4K 滚动文字素材，避免直接抓取平台画面造成水印和版权问题。

### 3. 现有数据工程缺口

当前 `SRVideoDataset` 对所有视频均匀采样，没有按类别采样权重，也没有内置按类别切分的训练/验证集。这会造成：

- 新增类别后无法按类别控制采样比例；
- 验证指标无法分场景看；
- 很难定位“哪一类翻车”。

方案里应补：

- 按类别 8:1:1 切分训练/验证/测试；
- 每个 epoch 按类别均衡或按权重采样；
- 验证时输出分场景 PSNR/SSIM/LPIPS；
- 对每类保留一小批人工可见的截图/短视频评测集。

## 四、建议执行方案

### P0：先用现有 907 段完成 v1 ×2 真权重

1. 对现有 6 类 + urban 做一次质量审计：
   - 清理损坏文件、重复片段、明显跑题素材；
   - 重点检查 `text_ui` 是否混入大量非 UI 内容，`urban` 是否真的以建筑几何为主；
   - 同步更新 `MANIFEST.json` 和开发进度文档。
2. 实现按类别 8:1:1 切分和分场景验证指标。
3. 在用户原生 GPU 环境跑短训练，确认 `g_loss` 稳定且无 NaN。
4. 再跑正式训练，导出 ×2 FP16 ONNX。
5. 用独立测试集实测：
   - 分场景 PSNR/SSIM/LPIPS；
   - 1080p→4K 实际 fps、显存、耗时；
   - 人物、文字、低光、高速运动人工目检。

### P1：补数据

1. 新增 `food`、`animal`、`art` 三类，每类先按 40~60 段采集；
2. 更新 `fetch_public_sr_data.py` 的 `CATEGORIES` 和查询词；
3. 新增 `run_collect_food_animal_art.bat` 或类似脚本；
4. 在 `text_ui` 下新增 `danmaku`、`screen_recording` 子目录并补 30~50 段；
5. 采集完成后重新审计、重建训练/验证切分。

### P2：不纳入本方案

录屏和弹幕只作为训练素材子类，不纳入软件功能开发。

## 五、最终建议

不要为了凑 9 类 850 段而暂停训练。正确顺序是：

1. 现有 907 段足够先训练 v1 ×2，验证“自研权重 + 推理 + 导出”全链路；
2. 训练和推理实测数据回来后，再用真实短板决定补哪些类别；
3. 食物/动物/艺术作为扩展类，弹幕/录屏作为 `text_ui` 子类，都放到 v1 验证之后补；
4. 录屏和弹幕不按产品功能做，只按训练数据补。
