## 一、打包体积与文件构成

### 1.1 实测数据

| 维度 | 数值 | 说明 |
|---|---|---|
| 磁盘总占用 | **67 GB** | 含大量 gitignore 的媒体/构建产物 |
| `git` 实际跟踪工作树 | **894 文件 / ~224 MB** | 这才是「源码交付物」体量 |
| `.git` 仓库对象 | **2.4 GB** | 含 LFS 本地缓存 + 完整历史（pack 最大 975MB） |
| `data/` | 60 GB | 1128 个 mp4 测试媒体，**已 gitignore** |
| `target/` | 615 MB | Rust 构建产物，**已 gitignore** |
| `gui/node_modules/` | 556 MB | **已 gitignore** |
| `target-srverify/` | 187 MB | **已 gitignore** |

**结论**：`git clone` 不含那 60GB+ 媒体与构建产物，仓库本体仅 224MB 工作树 + LFS 指针。真正「胖」的是被 gitignore 的本地媒体/构建目录——它们不会被打包上传。

### 1.2 这 224MB 到底装了什么（关键）

Top 大文件实测：

| 文件 | 大小 | 性质 |
|---|---|---|
| `python/models/sr_v0_test.random_before_20260808.onnx` | 34MB | SR **测试/random 权重**（非真权重） |
| `python/models/sr_v0_test.pth` | 34MB | 同上 |
| `python/models/sr_v0_test.onnx` | 34MB | SR 测试权重 |
| `python/models/sr_v1_test.onnx` | 18MB | SR 测试权重 |
| `gui/public/fonts/NotoSansSC-Regular.ttf` | 11MB | 中文字体（运行必需） |
| `gui/public/fonts/NotoSansSC-Bold.ttf` | 11MB | 中文字体（运行必需） |
| 其余字体 / `vendor/*.crate` | 1–9MB × 640 个 | 字体 + Rust 依赖源码包 |

**构成拆解**（约数）：
- SR 模型权重（LFS）：**~120 MB** —— 且是 `random_before`/测试权重，真权重按 `python/keying/models/` 规则 gitignore
- 字体 `.ttf`（LFS，运行必需）：**~32 MB**
- `vendor/` 634 个 `.crate`（Rust 依赖源码包）：**~73 MB**
- 真正的源码 + 文档 + 配置（rs/ts/tsx/py/md/json…）：**< 5 MB**

> ⚠️ **震撼事实**：git 跟踪的 224MB 里，**约 95% 是二进制（LFS 权重+字体）和死重 vendor**，真正源码不足 5MB。

### 1.3 Git LFS 真相（最容易算错的点）

`.gitattributes` 已配置 `*.onnx / *.pth / *.pt / *.ttf → filter=lfs`。实测 `git cat-file` 确认 `sr_v0_test.onnx` 在 git 中是**指针文件**（`version https://git-lfs.github.com/spec/v1`），非真二进制。

- **Push 到 GitHub 等远端**：仓库本体只含指针 + 源码（极小），二进制走 LFS 存储（需 LFS 配额 ~152MB，但其中 120MB 是浪费的 SR 测试权重）。
- **Zip 源码目录上传**：会带上 224MB 工作树（含 152MB 二进制 + 73MB vendor）。
- 本地 `.git` 2.4GB 是 **LFS 对象缓存 + 完整历史**，不属于上传体积，但说明历史里曾经塞过完整二进制。

### 1.4 瘦身建议（若现在打包上传）

| 动作 | 节省 | 说明 |
|---|---|---|
| 删除 SR 测试/random 权重（`sr_v0_test*.onnx/.pth`） | ~120MB LFS | 测试产物，真权重本就 gitignore |
| 删除或正确接线 `vendor/`（见 1.5） | ~73MB | 当前 cargo config 为空，纯死重 |
| 保留字体（LFS） | 0 | 中文渲染必需，不可删 |
| **理想干净交付** | **≈ 32MB（字体 LFS）+ <5MB 源码** | 仓库极瘦 |

### 1.5 `vendor/` 死重核实

`.cargo/config.toml` **文件存在但内容为空（0 字节）**，无任何 `[source.crates-io] replace-with = "vendored-sources"` 配置，源码也未硬编码引用 `vendor/`。即这 634 个 crate 源码包**完全没被 cargo 使用**，纯属历史残留。要么彻底删除，要么补上正确的 cargo vendor 配置让它真正用于离线构建（需评估是否真有必要离线）。

## 二、模块组合架构：monolith 还是「一切皆插件」

### 2.1 当前架构实际（以代码为准）

AIcut 是**清晰分层的单体（monolith）**，不是插件架构：

- **Rust 引擎**（`src/`）：媒体管线核心，导出双路径 `graph.rs`（简单工程一次性 ffmpeg filtergraph）+ `compositor.rs`（复杂工程 CPU 逐帧合成）；预览双路径 WebGPU 主 + HTML5 回退。
- **Electron 主进程**（`gui/electron/`）：IPC、导出编排、`exportOptions.ts`、`preload.ts`。
- **React/TS 渲染层**（`gui/src/`）：时间轴、属性面板、预览、字幕/转场/抠像 UI。
- **Python 推理桥**（`python/`）：MODNet 抠像、超清 SR、ASR，通过 bridge 与 Rust/Electron 通信。
- 模块间通过 **IPC + 共享 zustand store + sentinel assetId（`_text`/`_subtitle`）** 协作，紧耦合、编译期确定。

**这是一个性能敏感、媒体管线为核心的桌面应用，monolith 是合理基线。**

### 2.2 DeepSeek Harness 调研结论（联网核实）

| 项 | 结论 | 来源 |
|---|---|---|
| 是否真实存在 | **是**，DeepSeek 官方 2026-08-13 开源，MIT，命令 `dsh`，仓库 `deepseek-ai/deepseek-harness` | github.com/deepseek-ai/deepseek-harness |
| 定位 | **面向 LLM 的 Agent 运行时**（"Model + Harness = Agent"），连接模型与文件系统/终端/工具/子 Agent 的「执行外壳」 | deepseek.com/harness |
| 「一切皆插件」来源 | **非 DeepSeek 首创**，源自其底层 **Cordis 元框架**（Shigma，原 Koishi 插件内核，口号"插件即一切"） | github.com/cordiverse/cordis |
| 核心理念 | 服务挂共享 Context（`ctx.llm`/`ctx.tools`）、依赖注入、类型化事件（emit/waterfall/parallel/serial）、`ctx.effect()` 可逆副作用支撑热插拔 | tonybai.com/2026/08/14 解读、floatboat.ai/blog |
| 是否通用应用插件框架 | **否**，本质是「调模型 + 编排工具」的壳，擅长拼 coding agent，不擅长组织视频剪辑器内部模块 | 同上 |

**关键澄清**：用户把「DeepSeek Harness」和「一切皆插件」混在了一起。Harness 是 LLM agent 运行时；「一切皆插件」是它的底层 Cordis 内核的理念。二者都**不是为组织视频剪辑桌面应用内部模块设计的**。

### 2.3 是否该引入 DeepSeek Harness 来做模块组合

**结论：不需要，也不合适。**

- 用 DeepSeek Harness 来重组「导出/预览/转场/字幕/抠像」属于**用途错配**——它是调 DeepSeek 模型做 agent 任务的壳，不是应用插件框架。
- 若真要插件化，可复用的只有其**底层 Cordis 内核**（或 Python Pluggy / 自制扩展 API）作扩展层，而非整套 agent 运行时。

### 2.4 推荐架构：**单体内核 + 插件外缘**

| 层 | 策略 | 理由 |
|---|---|---|
| 媒体管线（Rust 导出/预览/转场/抠像） | **保留 monolith** | 性能敏感、紧耦合、需零 IPC 开销 |
| 外缘 AI 能力（ASR、智能抠图模型切换、导出预设、第三方滤镜、UI 面板） | **可插件化** | 低频、易隔离、可热插拔、利于第三方扩展 |

**代价 vs 收益**：全插件化对实时剪辑器风险高（启动开销、IPC 通信成本、跨进程调试难、版本耦合）；局部插件化收益最大（第三方滤镜/预设/AI 后端可替换）。

### 2.5 你没想到的点（补充）

- **「插件化」和「是否用 DeepSeek 模型」是两件事**：即使不引入 Harness，也可以在 AI 能力层做模型后端抽象（已有 `provider` 链 CUDA→DML→CPU 思路可扩展）。
- **Cordis 的 `ctx.effect()` 可逆副作用**才是「热插拔」精髓，若未来真做插件，重点学这个机制，而非 Harness 的 agent loop。
- 当前 sentinel assetId（`_text`/`_subtitle`）其实是**一种轻量「虚拟插件」思路**——用约定式 assetId 解耦渲染层与资产层，可作为未来插件化的雏形，无需引入外部框架。

## 四、补充建议（你可能没想到的）

1. **LFS 配额陷阱**：仓库虽小，但 LFS 存储按字节计费。SR 测试权重 120MB 纯浪费，删掉立省配额且加速 clone。
2. **`vendor/` 73MB 是「假装离线构建」的半成品**：要么删，要么真正配 `.cargo/config.toml` 启用 vendoring——现在两头不靠。
3. **导出双路径是长期风险源**：每次加 crop/flip/rotate/字幕/转场都必须在 `graph.rs` 与 `compositor.rs` 同步实现 + 加对称回归测试（已在 AGENTS.md 红线，但缺自动化卡点）。
4. **预览双路径同理**：WebGPU 与 HTML5 回退必须对称（crop 历史 bug 已印证）。
5. **`data/` 60GB 测试媒体永远别进仓库**：已 gitignore，但上传打包时注意别手滑 `git add data/`。
6. **记忆/文档散落**：`.workbuddy/memory/`、`docs/` 多份进展报告、根目录数份 `.txt` 建议——建议结项时归档为一份 `docs/设计决策记录.md`。
7. **未提交改动**：当前 `git status` clean（无遗留未提交），之前 SRT 与轨道管理均已提交（commit `4e11e67`、`5bc365c`），可放心结项。
8. **跨平台冻结**：若未来要 macOS/Linux 构建，当前大量 Windows 专属路径（venv、模型绝对路径、`.exe` 引擎名）需参数化。

## 五、总结

- **体积**：干净交付可压到 ~32MB（字体 LFS）+ <5MB 源码；当前 224MB 工作树里 95% 是 SR 测试权重（应删）+ 死重 vendor（应删/接线）+ 必需字体。Push 走 LFS，本体极瘦。
- **架构**：保持 monolith 内核，外缘 AI 能力可按需插件化；**无需引入 DeepSeek Harness**（它是 LLM agent 运行时，非应用插件框架），若插件化可借鉴其底层 Cordis 的 `ctx.effect()` 可逆副作用机制。
- **遗留**：最高优先级是 `compositor.rs` 丢字幕/转场（high）+ 已提交的 TEST HOOK 未清 + SR 真权重未接线；测试缺双路径对称回归。
- **本次未做任何代码改动**，仅做分析与报告。

> 附：本报告所有体积/配置/代码结论均经 `du` / `git` / `git lfs` / `grep` / `cat-file` 实测，关键误报已二次核实。
